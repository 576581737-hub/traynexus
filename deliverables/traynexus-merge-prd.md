## 一、产品目标

将 MemTrayCN v1.1 的成熟内存释放引擎与 Traynexus 的全新品牌体验融合，打造 **Windows 系统托盘一站式资源管家**：
- 保留并增强内存释放核心能力（StandbyList / WorkingSet / 组合释放，硬保护 + 白名单 + 阈值触发）
- 引入电池健康管理（充电上限控制 + 健康监控），填补 MemTrayCN 的功能空白
- 以 Traynexus 新品牌重新设计交互（iWatch 双环托盘图标 + 左键速览面板 + 极简右键 + Windows 风格主控制台）
- 建立可扩展的任务调度框架（时间/事件驱动自动化）
- 平稳迁移已有 MemTrayCN 用户的配置数据，做到零摩擦升级

**成功指标：**
1. 首版交付后，MemTrayCN 现有功能 100% 覆盖且体验不低于原版
2. 电池管理在主流品牌笔记本（Lenovo / Dell / HP / ASUS）上覆盖率达到合理比例
3. 已有 MemTrayCN 用户的配置文件自动迁移，无需手动操作
4. 安装包无需用户额外安装运行时环境（遵循 MemTrayCN 传统）

## 四、待确认问题清单

### 1. 合并范围（P0/P1/P2 边界确认）

**问题：** 以上 P0/P1/P2 优先级划分是否符合预期？特别是：
- 电池管理（R19-R23）放在 P1 —— 作为 Traynexus 的核心差异化功能，是否需要提升到 P0？
- 任务调度框架（R24-R26）放在 P1 —— 自定义调度规则的实现复杂度较高（需后端定时器 + 事件监听），首版是否先只做内置三条规则（R25）而将自定义推迟？
- 亮度（R28-R29）和电池校准（R30）放在 P2 —— 确认首版不纳入？

**建议：** P0 聚焦"内存释放引擎迁移 + 新品牌交互 + 配置迁移"，保障 7 月可发布最小可用版本（MVP）。P1 电池/调度在 MVP 验证后紧随迭代。

### 2. 配置目录迁移策略

**背景：** MemTrayCN 配置位于 `%APPDATA%\MemTrayCN\`，Traynexus 需迁移至 `%APPDATA%\Traynexus\`。

**推荐方案：** 自动迁移 + 兼容读取。

| 场景 | 行为 |
|------|------|
| 新用户（两个目录均不存在） | 在 `%APPDATA%\Traynexus\` 创建默认配置 |
| MemTrayCN 老用户（旧目录存在，新目录不存在） | 首次启动自动将 `MemTrayCN\` 下所有文件复制到 `Traynexus\`，成功后弹 Toast 提示"已从 MemTrayCN 迁移配置"，保留旧目录不删除（用户可自行清理） |
| 双目录均存在（用户曾手动操作或重复迁移） | 以 `Traynexus\` 为准，不覆盖；弹提示"检测到新旧配置目录同时存在，当前使用 Traynexus 配置" |
| 只存在新目录 | 正常使用 |

**待确认问题：**
1. 旧目录 `%APPDATA%\MemTrayCN\` 是否保留（不删除）？还是迁移后自动删除？
2. 若旧目录配置与新目录配置冲突（用户曾在两处分别修改），以哪个为准？
3. 是否需要提供"导出配置 / 导入配置"功能供用户手动迁移？

### 3. 技术栈产品约束

**产品要求（不给架构师绑死具体框架）：**

| 约束维度 | 产品要求 | 优先级 |
|----------|----------|--------|
| **运行时依赖** | 不建议要求用户额外安装运行时（如 .NET 8 Runtime、Python、Node.js）。MemTrayCN 的传统优势是"双击即用"（.NET Framework 4.x 系统自带），建议继承此特性 | P0 |
| **安装包大小** | 无硬性限制，但建议控制在 **50MB 以内**（避免用户下载犹豫）。如因技术栈原因超出此范围，需评估合理性 | P1 |
| **原生性能** | 内存操作（SetProcessWorkingSetSize / NtSetSystemInformation）必须低延迟，不存在 WebView 到后端的明显延迟感（<500ms 响应） | P0 |
| **权限要求** | 必须保留管理员权限（StandbyList 清理需要），但首次 UAC 弹窗后可后续通过任务计划程序静默启动 | P0 |
| **UI 渲染** | 托盘图标必须原生渲染（不能是 WebView 注入），速览面板和主控制台可接受 Web 技术栈 | P0 |
| **兼容性** | Windows 10/11 x64；对 Windows 7 的支持不做硬要求 | P1 |

**待确认问题：**
1. 是否接受 **WebView2 作为运行时依赖**（Windows 10 1809+ 通过系统更新自动获得，Windows 11 预装）？还是必须连 WebView2 都内置打包（会增加安装包 ~120MB）？
2. 若不使用 WebView2，Tauri 的 WebView 在部分精简版 Windows 上可能缺失 —— 是否接受"不支持极限精简版 Windows"？
3. 后端语言建议：C#（与 MemTrayCN 代码复用度高） vs Rust（Tauri 原生，电池/WMI 操作需额外库）—— 产品不绑死，但建议架构师评估代码复用效率。

### 4. 托盘交互模式

**两种方案对比：**

| 操作 | MemTrayCN（旧） | Traynexus 原型 | 推荐方案 |
|------|----------------|----------------|----------|
| 左键 | 无操作 | 弹出速览面板（Ultracode + 电池 + 一键释放） | **采用 Traynexus 方案** |
| 右键 | 9 项菜单（释放/面板/方式/阈值/白名单/配置/自启/关于/退出） | 4 项极简菜单（控制台/偏好设置/关于/退出） | **采用 Traynexus 方案** |
| 一键释放入口 | 右键菜单第一项 | 左键速览面板按钮 + 右键"打开控制台"→内存释放页 | **左键速览更便捷** |

**推荐：** 采用 Traynexus 左键速览 + 右键极简模式。

- 理由：左键速览是更直观的操作入口（符合 Windows 10/11 系统托盘设计趋势：网络/音量/电池皆是左键弹出面板）；右键精简减少认知负荷
- 兼容考虑：在"偏好设置"中保留一个"经典右键菜单模式"开关（P2），供深度 MemTrayCN 用户切换回 9 项菜单，降低迁移阻力

**待确认问题：**
1. 是否需要"经典右键菜单模式"兼容开关？
2. 一键释放功能在速览面板中直接提供 + 主控制台也可触发 —— 是否还需在右键菜单保留"一键释放"快捷入口？建议不加（保持极简），用户可通过左键速览触发。

### 5. 电池模块兼容性处理

**背景：** 充电上限设置依赖厂商特定的 WMI 接口或驱动 API：
- **Lenovo**: `Lenovo_SettingsDependency` WMI 类 / Lenovo Vantage API
- **Dell**: `Dell_SMBIOSSettings` WMI 类 / Dell Power Manager
- **HP**: HP Battery Health Manager（BIOS 层面）/ HP Power Manager API
- **ASUS**: ASUS System Control Interface (ASUS WMI)
- **通用 Windows**: `PowerSetActiveScheme` + 自定义电源计划（非直接控制充电上限，仅间接影响充电行为）

**产品降级策略：**

| 场景 | 行为 |
|------|------|
| 检测到支持的 OEM | 正常启用充电上限设置，设置后立即生效 |
| 未检测到支持的 OEM，但 WMI 电池信息可读 | 充电模式选项灰显 + Tooltip："当前设备不支持软件控制充电上限。请使用厂商自带工具（如 Lenovo Vantage、Dell Power Manager）或 BIOS 设置。" |
| 电池信息完全不可读（台式机） | 充电管理页显示"未检测到电池"提示，隐藏充电相关功能 |
| 充电上限设置失败（API 返回错误） | Toast 提示"设置失败：请确认已安装最新厂商驱动"，恢复上一次有效设置 |

**最低要求（P0）：** 无论硬件支持情况如何，电池电量百分比读取（`Win32_Battery.EstimatedChargeRemaining`）必须正常工作并显示在托盘图标内环和速览面板中。

**待确认问题：**
1. 首版需要支持的 OEM 品牌范围？建议：**Lenovo + Dell + HP + ASUS** 四家主流品牌
2. 对于不支持充电上限控制的设备，是否需要提供替代方案（如通过 Windows 电源计划间接实现"插电时不充满"）？还是直接告知不支持？
3. 是否需要提示用户"安装厂商驱动以获得完整电池管理功能"？
